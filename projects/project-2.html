PROJECT 02.

화장품 매장 판매 분석 시스템

6인 팀 · Java·MySQL 기반 화장품 매장 판매 분석 시스템 개발, 고객 이력 테이블 설계와 입력·조회 기능 담당. 가격·고객 정보가 바뀌어도 과거 매출이 주문 당시 기준으로 집계되도록 설계.

핵심 결과

  • 01

    주문 당시 기준

    가격이 바뀐 뒤에도 과거 매출 집계

  • 02

    검증 + 롤백

    누락·중복 데이터와 일부만 저장되는 일 방지

개요

기간
약 3주
인원·역할
6인 팀 / 고객 이력 테이블 설계, 입력·조회 기능
도구
Java, MySQL

01문제 정의

배경
매장의 가격과 고객 정보는 시간에 따라 변경
해결하려던 문제
정보 변경 시 지난 매출까지 새 값으로 재계산되면 분석 결과 신뢰 불가
목표
과거 매출의 주문 당시 기준 집계, 잘못되거나 일부만 저장된 데이터 방지

02데이터와 방법

다룬 데이터
고객 이력·상품·주문 데이터 (MySQL)
담당 기능
고객 이력 테이블 설계, 입력·조회 기능
사용 도구
Java, MySQL (PreparedStatement, 트랜잭션)

핵심 행동과 결과

  • 01

    문제해결

    가격 변경 시 지난 매출까지 새 가격으로 재계산될 위험

    How + Result주문 시점의 단가를 별도 칼럼에 저장 → 과거 매출을 주문 당시 기준으로 집계

  • 02

    데이터 정합성

    고객 정보가 바뀌어도 주문 당시 고객 상태 기준 분석 필요

    How + Result주문일을 고객 이력의 유효 기간과 맞춰 조회 → 당시 상태로 집계

  • 03

    안정성

    잘못되거나 일부만 저장된 데이터 방지 필요

    How + ResultPreparedStatement 바인딩, 저장 전 검증(필수값 누락·없는 고객/상품·중복 상품), 트랜잭션 롤백 → 누락·중복·일부 저장 차단

03결과

항목별 판단 기준과 결과
항목 판단 기준 결과
과거 매출 집계 가격이 바뀐 뒤에도 주문 당시 단가로 집계 주문 당시 기준으로 집계되는 것 확인
잘못된 입력 필수값 누락·없는 고객/상품·중복 상품은 저장하지 않음 저장 전에 걸러냄
저장 중 오류 일부 데이터만 저장되지 않음 트랜잭션 롤백
확인 방법
가격 변경 후 과거 매출을 다시 조회해 주문 당시 기준 집계 여부 확인

04막혔던 부분과 해결 과정

  • 문제 상황

    가격·고객 정보 변경 시 지난 매출까지 새 값으로 재계산 → 분석 결과를 믿을 수 없게 될 위험

    Point과거 매출은 나중에 바뀌면 안 되는 기록

  • 해결책

    주문 시점 단가 별도 칼럼 저장, 조회 시 주문일과 고객 이력 유효 기간을 맞춰 당시 상태로 집계

    Point가격 변경 후에도 과거 매출이 주문 당시 기준으로 집계됨을 확인

  • 비교 대상

    은행 거래: 거래가 끝난 뒤에도 그 시점의 금리·금액이 그대로 남아야 하는 것과 같은 원리

    Point데이터 이력을 정확하게 보존하는 것이 신뢰의 기반

05AI 도구 활용

사용한 도구
ChatGPT
맡긴 작업
고객 이력 테이블(유효 기간) 설계 방식 조사, PreparedStatement·트랜잭션 예시 코드
검증 방법
가격 변경 후 과거 매출을 다시 조회해 당시 기준 집계 확인, 누락·중복 값을 넣어 저장 차단 확인
직접 고친 부분
저장 로직을 트랜잭션으로 묶어 오류 시 롤백되도록 수정

06배운 점

배운 점
